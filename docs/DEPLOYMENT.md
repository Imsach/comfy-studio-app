# Deployment

This repo has no deployment code of its own — the container, the GPU wiring, the
auto-update timer, and the dashboard/monitoring entries are all generated by and
version-controlled in a separate repo: `github.com/Imsach/proxmox-homelab`. This
doc is the pointer for anyone in *this* repo who needs to know how it actually runs.

## Where it runs

Deployed as **CT113 ("Mufiji")** on a personal Proxmox homelab —
`scripts/10-deploy-comfystudio.sh` in the homelab repo; full writeup in that repo's
`README.md` §10.6.

Runs as the **Vite dev server** (`vite --host 0.0.0.0`), not a production build —
deliberately, not a shortcut. The ComfyUI reverse proxy
(`/comfyui-proxy` in `vite.config.ts`) is implemented as a Vite dev-server
middleware (`configureServer`), which does not run under `vite build` + `vite preview`
or any static file host — it's dev-server-only by Vite's own plugin API. If this ever
moves to a production build, that proxy needs reimplementing as real server middleware
(Express/Fastify in front of the static build) first, or `/comfyui-proxy` silently stops
working.

**Auto-update:** a systemd timer polls `main` every 15 minutes and redeploys on a new
commit (`git reset --hard` + `docker compose up -d --force-recreate`) — not a webhook,
so there's up to a 15-minute lag after a push, and a brief (~15-20s) restart on deploy.

## GPU servers — on-demand, not always-on

The four ComfyUI servers this app talks to (two boxes, two GPUs each — see in-app
Settings → ComfyUI Servers) don't run continuously. One of those boxes has a real prior
incident where ComfyUI was deliberately killed to free VRAM for ML training work, so
each instance now starts on the first real request and stops again after 10 minutes at
0% GPU utilization — the same idea as Ollama's keep-alive. Implementation:
`scripts/comfyui-ondemand-proxy.py` / `comfyui-idle-watch.py` in the homelab repo, run
on the GPU boxes themselves (not this container). Full incident history is in the
scanstocks repo's `docs/GPU_TRAINING_RUNBOOK.md` (yes, a different repo — that's where
those two GPU boxes are otherwise documented).

**If a configured server shows "No GPU detected" or "Cannot reach ComfyUI":** that may
just mean it's asleep, not actually broken — check `GET /system_stats` directly rather
than assuming from the app's status panel, since the on-demand proxy deliberately
refuses that exact endpoint while idle (it's what the app itself polls every 10s for the
status panel, and treating that as "wake up" would have kept every instance permanently
busy — see the proxy script's own docstring). Sending an actual generation request wakes
it; that takes a few seconds.

## Known gaps in this app's own config handling

Found while wiring up the deployment above — not fixed here, just documented so nobody
re-discovers them from scratch:

- **`VITE_COMFYUI_URL` in `.env` is effectively decorative.** `src/services/comfyClient.ts`
  / the settings store hardcode `http://localhost:8188` as the fallback and never read
  the env var. On a genuinely fresh browser with empty `localStorage`, the app tries to
  reach ComfyUI at `localhost` **from the browser's own machine**, which almost never has
  anything listening there — first load sits on "Cannot reach ComfyUI" until someone
  fills in the Settings form by hand. Not a deployment bug, just a UX gap worth fixing
  upstream at some point (read the env var as the initial default instead of a hardcoded
  localhost).
- **`checkConnectionWithUrl` in `comfyClient.ts` requests `'\system_stats'`** (backslash,
  not `/system_stats`). JS silently drops the meaningless backslash escape, so it
  actually requests path `system_stats` with no leading slash — harmless if
  `proxyFetch`/the URL constructor normalizes it, but worth fixing to the literal
  intended string next time that file's touched.
- **All server config lives in browser `localStorage`** (`comfyui-app-settings`), not
  anywhere server-side — confirmed by reloading and re-reading the saved form, not
  assumed. Clearing site data / a different browser means re-entering all four GPU
  servers and the Ollama settings from scratch.
